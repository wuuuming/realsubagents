# Architecture review after G0.05 — 2026-11-10

Scope: `docs/design.md` (rev 2.1) and the v0.1–v0.4 route, checked against what v0.0 and v0.05 measured (reports 001–003). The question: what does the evidence say about the design, and what should be built next?

## 1. What the evidence says

| Design assumption | Evidence | Verdict |
|---|---|---|
| Splitting saves **cost** through the quadratic read term (§1, §15.1) | Cache reads cost $0.2/Mtok, 1/25 of a write. Reads are only ~35% of a large session's cost. With prompts v1 the median cost was 89%, and the model puts a 20% saving at ~150 calls per session, 2.5× our large tasks | **Weak at real task sizes.** Cost parity, not savings |
| Splitting saves **time** | 63% median, and ~50% on 10–12 min tasks, once workers stop re-verifying and the split is balanced | **Holds.** This is the product |
| Module-scoped context makes workers grow slower (g\_w < g) | g\_w 1.67 k vs g 1.53 k per call; P\_w ≈ P. Workers re-read what they need, brief or not | **Not observed** |
| An orchestrator can split well | 24 of 24 runs accepted, 0 merge conflicts. v1 balanced the work by file inside a package when needed. Split took ~28 s | **Holds, without Partitioner or G0** |
| Workers verify, a review verifies again (§14) | v0: per-worker suites made the slower worker 2× slower. v1: workers run targeted tests, one integration check, 12/12 correct | **Verify once, at integration** |
| Orchestrator overhead stays small (H-5) | 10% (v0), 15% (v1), because it now runs the integration check | **At the limit** |
| Serial fraction < 25% (H-3) | 48%: split ~28 s + tail ~51 s + check ~42 s out of ~5 min | **Fixed costs dominate short runs** |
| Small tasks must stay at baseline cost (§1) | Not measured yet, but the only fixed cost before escalation is one tool description (~300 tokens) | Likely fine |

**Conclusion.** The mechanism that worked is short-lived: *split → isolated seeded worktrees → targeted tests → one integration check → merge*. The mechanisms that make up most of the design's size are unproven or contradicted by the data. These are long-lived module groups, G0, the Partitioner, contracts, the shared zone, merge trains, semif judges and regrouping.

## 2. Advice

### A. Restate the goals to match the evidence (design §1)

- Large parallel tasks: **time ≤ 75% (k = 2), cost ≤ 100%**, instead of cost ≤ 80%. Cost savings stay a hypothesis for very long sessions (n ≳ 150 calls), to be tested in v0.3 with lanes and long tasks, not promised in v1.
- Escalation (§7.2) should trigger on **expected time gain**, not on cost break-even. That means ≥ 2 separable parts of comparable size, *and* an expected single-session duration of ≥ ~6 min. Below that, the fixed ~70 s (split + merge + check) eats the gain: our 6 min tasks reached 75–83%, the 10–12 min ones ~50%.

### B. Re-sequence: productise the proven loop first

The route's v0.1 is "orchestrator + G0 + **one** group, in-process". One group has no parallelism, and v0.05 showed workers get no context advantage, so v0.1 as planned would ship overhead with no measurable benefit. In-process SDK sessions would also share one process (no per-worker cwd, no fault isolation), while v0.05 already proved the subprocess path.

Proposed new order (D-28):

| Phase | Content | Gate |
|---|---|---|
| **v0.1 Split runtime** | The v0.05 loop as a real extension in the user's session: `rsa_split` (k workers), `rsa_steer`, `rsa_finish`; worker subprocesses in seeded worktrees; Reports as messages; merge + integration check run by code; durable state (SQLite) so a killed `pi` resumes; simple escalation hint | Reproduces v1's numbers on the 4 large-parallel tasks through the extension, not the bench relay; small-task overhead ≤ +3%; kill/resume test |
| v0.2 Robustness | Watchdog, scope guard (block writes outside a worker's paths), leftover-process cleanup, k = 3, a task queue so a second request can run while one is in review | k = 3 run; H-3 improvement |
| v0.3 Long tasks | Lanes inside one part, scouts, and the cost hypothesis on long sessions | Cost ≤ 80% on n ≳ 150 tasks, or drop the cost goal |
| v0.4+ | Long-lived groups, G0, Partitioner, contracts, regrouping, only if v0.2/v0.3 data shows a need (e.g. repeated tasks in one module where warm context pays) | — |

### C. Cut or defer, with the reason

| Mechanism | Why defer | What replaces it for now |
|---|---|---|
| Long-lived groups (§3, §4) | Provider caches live 5 min, so a "warm" worker is usually cold by its next task; P\_w ≈ P shows no context advantage | Disposable workers per task; realctx path-keyed memory carries knowledge across tasks |
| G0 + Partitioner + bootstrap (§7.1) | The orchestrator split all 24 runs correctly from reading code | A deterministic repo outline (workspace packages, sizes, test commands) given to the orchestrator to shorten the split |
| semif completion / merge-risk judges (§14) | Tests + one orchestrator check gave 24/24 correct | Tests run by code; the orchestrator reads the result |
| Contracts and shared zone (§13.3) | 0 conflicts in 24 runs; shared files (changelogs) were given to one worker by the prompt | Prompt rule plus merge-conflict handoff (already in the relay) |
| Merge trains with bisection (§6) | One task at a time in v0.1 | Plain merge into an integration branch |
| Full event sourcing with replay (§10–12) | Durability needs a transactional store; replay is a nice-to-have | SQLite tables with an append-only `events` log written in the same transaction; no generic rebuild in v0.1 |
| In-process GroupRuntime | No per-session cwd, no fault isolation | Subprocess workers only |

### D. Concrete improvements from the data

1. **Integration check by code.** The orchestrator names the check commands in its dispatch, and the runtime runs them after the merge and returns pass/fail plus failing test names. This saves orchestrator calls (H-5) and part of the ~42 s check (H-3).
2. **Shorter split.** Put the deterministic repo outline in the `rsa_split` tool's description or first result, so the orchestrator reads less before dispatching.
3. **Report length.** Summaries were 600–900 characters against "3 lines". Enforce with `maxLength` in the tool schema; the orchestrator pays output for them at $20/Mtok.
4. **Prefix sharing (small).** Pi's system prompt ends with `<cwd>`, so workers in different worktrees cannot share a prefix cache write (~$0.07 per extra worker). Not worth a workaround now; note it upstream.
5. **No upstream dependency in v0.1.** §17.1 lists 10 changes to realctx and realtasks. v0.1 should need none (the relay needed none), so it ships on today's versions.

### E. Risks

- **Windows process leaks:** background tasks outlive Pi. The product needs `killLeftovers` per worker tree, as the bench does.
- **Budget:** $105.99 of $215 left. Reproducing v1 through the extension (12 runs, ~$22) + small-task overhead (6 runs, ~$5) fits; one full measurement in v0.2 (~$30) fits; v0.3's long-task test needs new tasks and is the uncertain part.
- **Model drift:** the baseline is valid only for Opus 5.5, Pi 1.5.0 and realctx `90b356c`. An upgrade before v0.2 costs ~$50 to redo.

## 3. What is being built now (no-regret under either order)

These are needed whether or not D-28 is accepted:
1. `src/store/`: SQLite state store (tasks, workers, events in one transaction, WAL, forward-only migrations), with tests.
2. `src/runtime/`: the worker subprocess runtime and the tree manager, extracted from `bench/dryrun.ts` and `bench/run.ts`, so the bench and the extension share one implementation.
