Two unrelated problems in two packages. Fix both; the fixes are independent of each other.

1. **packages/tui: OSC 133 markers break terminal status.** In regular (non-fullscreen) TUI mode, user and assistant messages write OSC 133 shell-integration markers (`\x1b]133;A`, `B`, `C`, terminated by BEL or `ESC \`) straight to the terminal. Terminals that show OSC 7501 program status (Rex, iTerm2 3.7.5+) read `133;A` as a new shell prompt and drop the current status, so the "working" indicator disappears right after a run starts (#11565). Fullscreen mode is not affected because it already strips these markers before writing. Regular mode (`TuiMainScreen`, `src/tui-main-screen.ts`) must not write OSC 133 markers either; the components keep producing them (fullscreen uses them for prompt navigation), and the rest of each line must still be written.

2. **packages/coding-agent: `pi update --extensions` claims success when npm installed nothing new.** Pi looks up the newest version of each npm package with `npm view` and runs `npm install <name>@latest` when it is newer than the installed one. Shortly after a publish, `npm view` can already report the new version while `npm install` still resolves the old one; npm exits successfully, Pi prints "Updated packages", and the same update is offered again on the next launch. After installing, Pi must re-read each updated package's installed version; if the registry lookup succeeded and the installed version did not change, the package manager emits a `progress` event (to the callback set with `setProgressCallback`) for that source, with a message like `<source> is still 1.0.0 (registry reports 1.0.1); npm registry metadata may be stale, try again in a few minutes`. Packages that did change get no such event. The package CLI must print `progress` events (in yellow); until now nothing emitted them. Install behaviour itself is unchanged.

Add tests for each, and keep the test suites of the two packages passing.
